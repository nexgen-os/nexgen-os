# Benchmark plan — the series package on managed Postgres

Status: planned, not executed. Taken from §4 of
[audit-series.md](audit-series.md) (2026-10-19) and written against the
functions the series package ships (`store()`, `resample()`,
`nexgen.window()`, `latest()`, `coverage()`, `forecast_at()`,
`export_rows()`, `series_rollup()`). The figures it produces go into a dated
note beside this one; this page does not change once the run is made.

## Dataset

One real site with its time zone.

| Set | Size | Rows |
|---|---|---|
| A | 50 meters × one quantity at 15 minutes for one calendar year | 50 × 35,040 = 1,752,000 |
| B | the same 50 meters with three quantities each (offtake, injection, production) | 5,256,000 |
| C | one weather point with 5 hourly quantities | 43,800 |
| D | one forecast series issued daily with 48 hourly values | 17,520 |

Loaded with weekly partitions through pg_partman (and once through
`series_values_partition()` alone, to compare).

## Target instance

Supabase Micro, the smallest paid compute: shared CPU, 1 GB memory,
60 connections, 11 MB/s and 500 IOPS baseline
([Supabase compute and disk](https://supabase.com/docs/guides/platform/compute-and-disk),
accessed 2026-10-19). Every query runs as `authenticated` with JWT claims
set, so that row level security is in the plan, through SQL and through
PostgREST (`/rpc/<function>`); cold cache (after a restart) and warm; p50
and p95 over 20 runs.

## Operations

| # | Operation | Good on Micro (p95, warm) |
|---|---|---|
| W1 | bulk load of set A through `store()` in batches of 35,040 | ≥ 30,000 rows/s, under 60 s |
| W2 | one day for 50 meters (4,800 rows) | < 1 s; rollups fresh < 5 s after (`series_rollup()`) |
| W3 | the same day again (idempotent) | 0 rows changed, < 1 s |
| R1 | `nexgen.window()`: one meter, one year raw | < 150 ms |
| R2 | `resample()`: one meter, one year, hourly / daily / monthly | < 50 ms from rollups; the raw path measured too (a dirty hour in range) |
| R3 | 50 meters summed per 15 minutes over one month (one `resample()` per series today; an `aggregate()` function if it lands) | < 500 ms |
| R4 | 50 meters per month over one year | < 100 ms |
| R5 | `latest()` for 50 meters | < 20 ms |
| R6 | `coverage()`: 50 meters, one year, 3 % of days removed | < 300 ms |
| R7 | hourly production joined with irradiance and temperature, one year | < 200 ms |
| R8 | `forecast_at()` with `as_of` and with `horizon = 24 hours`, one year (set D) | < 200 ms |
| R9 | `export_rows()` for one week of 50 meters, written by `formats/parquet` | < 2 s |
| M1 | `series_rollup()` over a full year of dirty hours (set A) | < 60 s |

## Sizes to measure

`pg_total_relation_size` of `series_values`, of each weekly partition, of
the primary key and BRIN indexes, of `series_rollups`, `series_dirty` and
`series_latest`; the WAL generated by W1 (`pg_current_wal_lsn()` before and
after); the Parquet file of one week.

Expected from decision 0007's ~105 bytes per row: ~184 MB for set A and
~552 MB for set B; hourly rollups 438,000 rows and daily 18,250 for 50
series. "Good" is within 20 % of those figures, no query spilling to disk
at the default `work_mem`, and the whole of set A inside the instance's
memory once rolled up.

## What the run must also say

- The plan of each read (`explain (analyze, buffers)`), since under load
  the plan is the assertion, not the clock (Ekwo OS 0060): partitions
  pruned, the primary key used for `window()`, the rollups read for R2
  and R4.
- The cost of the statement trigger that marks dirty hours during W1,
  against a load with the trigger disabled.
- The cost of the step check of `store()` on a series with history (one
  index probe per call).
